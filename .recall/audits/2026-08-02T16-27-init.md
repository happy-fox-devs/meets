## Key verified facts (see individual nodes for full detail)

1. Custom server (`server.js`), not `next start` — dev/start/prod all run `node server.js`.
2. Auth: no meets-specific secret. `join-room` forwards the caller's real NestWorks JWT
   to the calendar backend's `/api/v1/academic/meets/authorize` endpoint; that backend's
   Spring Security is the sole real trust boundary.
3. The `userId` flowing through signaling events is literally the client's own
   `socket.id`, not a persistent user id — only `userName` (from the server-side
   authorize response) is a real identity signal.
4. Signaling relay (offer/answer/ice-candidate) is guarded by
   `authorizedPeerInSameRoom` — both ends must have passed join-room auth and share a
   room, closing an SDP-hijack path.
5. **TURN is not configured** — STUN-only (Google + Twilio public STUN), hardcoded
   identically in `createPeer` and `addPeer`. Verified live in code, matches
   `docs/turn-server.md`'s claim exactly. Flagged as the single biggest real-world
   reliability gap (participants behind symmetric NAT/corporate firewalls fail silently).
6. Full-mesh WebRTC topology, `MAX_ROOM_SIZE` (default 8, env-overridable) caps
   membership because mesh cost is O(n²).
7. No persistence layer anywhere — chat is relay-only (never stored), `userNames`/
   `socketRooms` are in-process `Map`s with no shared adapter, so this cannot
   horizontally scale past one instance as-is.
8. **Correction to a doc-adjacent artifact**: `lint.log` at the repo root is stale
   (UTF-16, references a pre-rename path `E:\Trabajos\happyfox\meets\...`, and its
   recorded parsing error at line 238 does not reproduce). Running `npx eslint .` live

   violations for `createPeer`/`addPeer`/`restartMedia` under the new

   `@typescript-eslint/no-explicit-any`). Both facts are now recorded as separate nodes

  Not a data-exposure issue, but a real availability gap: an unknown fraction of
  real-world users (symmetric NAT, corporate firewalls, some mobile carriers) cannot
  complete a call at all, with no error surfaced explaining why. Already tracked in
  `docs/turn-server.md` as unresolved backlog; this pass confirms the doc is still
  accurate and the gap is still open.
- **Low**: `ALLOWED_ORIGIN` defaults to `"*"` for Socket.IO CORS — explicitly documented
  as a dev-only fallback in README.md; real risk depends on whether production actually
  sets this env var (not verified in this pass — no deploy/env config was available to
  inspect).
- No other auth weaknesses found. The join-room -> authorize() -> per-relay
  `authorizedPeerInSameRoom` chain is a coherent, real server-side authorization design,
  not security theater. This is a meaningfully stronger posture than "room id as secret."
